# Membership plan catalogue

Implemented using the supplied `gym_schema.sql`, `implementation_Details.md`, and the existing migration chain. Membership Plans now uses dedicated queries, not `/gym/workspace`.

## Deploy

If migrations 001–004 are installed, apply only **`005_membership_plan_crud.sql`**, then restart the backend. Do not replay the initial schema or earlier migrations. No live migration was automatically applied during implementation.

Migration 005 adds `gym_plans.description` (empty for existing rows), `deleted_at`, a private read projection, checked RPCs, mutation audit records and an active-plan check for new subscriptions. Existing prices, durations, member subscriptions, invoices, payments and prior migration files are not rewritten. RLS/privilege rules close direct browser access; custom Google sessions authorize backend requests, not Supabase Auth policies.

## API

| Method | Path | Result |
| --- | --- | --- |
| GET | `/membership-plans` | All non-deleted catalogue plans, including inactive plans |
| GET | `/membership-plans/{id}` | One non-deleted plan |
| POST | `/membership-plans` | Create, HTTP 201 |
| PATCH | `/membership-plans/{id}` | Edit only supplied fields |
| DELETE | `/membership-plans/{id}` | Remove from catalogue, with explicit deletion mode |

Super Admin, owners and receptionists (`admin` in PostgreSQL) are allowed. Trainers, inactive users and users without a live permitted grant are denied. RPCs recheck the actor independently. Mutation requests require the configured frontend Origin, consistent with access-management CSRF protection. Actor IDs come from verified sessions; client-supplied IDs, computed counts and audit fields are rejected.

Create request:

```json
{
  "name": "30-day Essential",
  "price": 2500,
  "duration": 30,
  "durationUnit": "DAY",
  "description": "Gym access and group classes",
  "isActive": true
}
```

The database uses `duration_days`, so the API/form use **fixed calendar days only**. Months/years are not approximated as 30/365 days. Existing catalogue records are read directly as their stored day counts. Limits: name 2–120 trimmed characters, duration 1–36,500 whole days, nonnegative INR price fitting numeric(12,2), at most two decimal places, description up to 2,000 characters. Empty descriptions and free plans are supported. PATCH accepts any nonempty subset; explicit nulls are invalid.

Read responses use the same fields plus UUID `id`, `activeMembersCount`, and `hasHistory`. Counts are computed, not independently stored or writable. Active members are distinct members with active profiles and non-cancelled gym subscriptions covering today inclusively in Asia/Kolkata. Future subscriptions are not active yet; multiple qualifying subscriptions do not double-count one member. Disabling a catalogue plan does not cancel members already using it.

## Delete and history

```json
{ "id": "<plan UUID>", "mode": "DELETED" }
```

- Unreferenced plans are physically deleted. Audit events survive with source snapshots and a nullable live plan FK.
- Any plan referenced by `member_plans`, including cancelled/expired history, is retained with `active=false` and a deletion timestamp. It disappears from catalogue GET/list and cannot be edited/reactivated through the API. The response mode is **`REMOVED_FROM_CATALOG`**.
- Existing subscriptions keep their plan reference, purchase price, dates and lifecycle. Invoice items keep their original descriptions/amounts. No payments, invoices, memberships or renewals are generated by catalogue operations.
- The original name uniqueness constraint remains in place. Retained historical plan names stay reserved; create a distinctly named replacement rather than overwriting history. An unused, physically deleted plan's name can be reused.
- The UI confirmation explains both outcomes and shows the actual result after deletion. It never labels a retained historical row as permanently erased.

Writes are serialized and target rows locked before reference checks. New subscription inserts/plan-link changes take key-share locks and require an active, non-deleted plan, so a deletion racing a purchase cannot silently attach a new purchase to a removed plan. Foreign keys remain the final protection against lost references. Native multi-connection load/concurrency testing remains a deployment check.

Catalogue edits are last-write-wins; there is no optimistic version/ETag check. They affect future sales only, never rewrite contracted terms. Purchase/renewal endpoints must still calculate and persist dates/prices server-side and enforce their remaining member/billing rules; this feature is not a subscription-renewal implementation.

## UI and verification

The existing OpenDesign card/dialog styles are preserved, with real create/edit/delete forms, status/search filters, confirmation, loading, empty/error states, cache refresh and deletion feedback. Inactive plans can be re-enabled through Edit. Shared PT-plan management now uses the same aligned layout; see [trainer_plans.md](trainer_plans.md) and migration 006.

Tests execute the full supplied base schema and migrations 001–005 in a disposable PostgreSQL-compatible database. They verify free plans, validation, permissions, expiry counts, edits preserving price/date/invoice snapshots, safe deletion, inactive/deleted purchase rejection, audit retention and database-role restrictions. HTTP tests use real session guards with isolated database doubles; frontend tests exercise create/edit/delete and failure handling without a workspace API.

Run `python -m unittest discover -s tests` in backend and `npm test`, `npm run lint`, `npm run build` in frontend. Optional SQL execution: set PGLITE_MODULE to an isolated `@electric-sql/pglite/dist/index.js` installation and run `node --test tests/test_membership_schema.mjs`.

OpenDesign was unavailable during implementation; no new visual comparison or live Supabase deployment is claimed.

Verification: full suites passed with 55 backend tests, 40 frontend tests and 42 SQL checks, plus frontend lint and strict TypeScript/production build. Startup/OpenAPI generation confirms the GET/POST collection and GET/PATCH/DELETE item routes are registered.
