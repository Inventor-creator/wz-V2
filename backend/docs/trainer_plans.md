# Trainer plan catalogue

## Deployment

Apply **`006_trainer_plan_crud.sql` after migrations 001–005**, then restart the
backend. Do not replay `gym_schema.sql` or rewrite older migrations. This follows
`implementation_Details.md`; no live database migration is applied automatically.

006 adds `description`, `deleted_at`, a private read projection, mutation audit
events, checked catalogue RPCs, an index and a new-purchase validation trigger.
Existing catalogue IDs, global name uniqueness, durations, prices and assignment
foreign keys remain intact. Existing descriptions default to empty. No ownership
is guessed from names or past subscriptions.

## Shared plans, separate trainer selection

`trainer_plans` is a **shared catalogue**, not trainer-owned. A purchase in
`member_trainer_plan` references both `trainer_plan_id` and `trainer_id`; any active
trainer can deliver an active plan. Do not send a `trainerId` when editing the
catalogue. The frontend now reflects this contract, including the development
adapter and member form. Trainer details link to the shared catalogue.

The new **Trainer Plans** navigation entry at `/personal-training-plans` works
without `/gym/workspace`. Existing trainer profile/member/billing pages retain
their separate backend integration requirements; this is not a trainer-profile
CRUD, purchase, billing, renewal, or payout-write implementation.

## API

| Method | Path | Result |
| --- | --- | --- |
| GET | `/personal-training-plans` | Non-deleted plans, active and inactive |
| GET | `/personal-training-plans/{id}` | One non-deleted plan |
| POST | `/personal-training-plans` | Create, HTTP 201 |
| PATCH | `/personal-training-plans/{id}` | Update supplied fields |
| DELETE | `/personal-training-plans/{id}` | Delete/removal mode |

Request fields match membership plans: `name` (2–120 trimmed characters), `price`
(INR, 0–9,999,999,999.99 with at most two decimals), `duration` (1–36,500 whole
calendar days), `durationUnit` (`DAY` only, default), `description` (optional empty
string, up to 2,000 characters), `isActive` (boolean, default true). Create requires
name/price/duration; PATCH requires a nonempty subset and rejects explicit nulls.

```json
{"name":"PT Strength 30","price":6000,"duration":30,"durationUnit":"DAY","description":"One-to-one strength coaching","isActive":true}
```

Responses add UUID `id`, `activeMembersCount`, and `hasHistory`. Counts are distinct
active-profile members with non-cancelled assignments covering today inclusively
in Asia/Kolkata, across all trainers; future assignments do not count yet. Counts
are derived, not editable. Catalogue inactivity does not cancel existing purchases.

## History and deletion

- Unreferenced plans are physically deleted: `{"id":"...","mode":"DELETED"}`.
- Plans with any assignment history (including expired/cancelled) become inactive
  and receive `deleted_at`: mode `REMOVED_FROM_CATALOG`. They disappear from list/
  get and cannot be edited/reactivated. Historical names remain reserved.
- Events retain the actor, old/new state, timestamp and original UUID in snapshots;
  a physical deletion nulls only the live event FK.
- Catalogue edits affect future offers only. Subscription prices/dates/trainers,
  invoice descriptions/amounts, receipts, allocations, payout rules and payouts
  are never rewritten or generated by catalogue operations.
- New inserts and trainer/plan-link updates require an active non-deleted plan
  and active trainer. Lifecycle-only updates on historical assignments remain
  possible after catalogue removal. Renewals must create a new assignment.
- Row locks serialize catalogue writes and protect plan/trainer availability
  against concurrent purchase inserts. Native multi-connection load/concurrency
  testing remains a deployment check; the disposable SQL suite is single-connection.
- Edits remain last-write-wins, matching membership plans (no ETag/version check).

## Security and verification

Super Admin, owners and receptionists can manage plans. Trainers cannot. The
backend resolves verified Google sessions and live roles; SQL checks the actor
again using the guard from 005. Browser DB roles have no catalogue/RPC access.
Only checked RPC execution and required raw catalogue reads are granted to the
backend role. Mutations use the existing Origin guard, reject unknown/readonly
fields, and create audit events. Existing OAuth behavior is unchanged.

Local tests cover the full migration chain, existing data preservation, shared
plans, inclusive/distinct counts, free plans and validation, live role checks,
safe deletion/auditing, new-purchase status checks and full assignment/invoice/
payment/allocation/payout snapshot preservation. HTTP tests use isolated database
doubles with session/origin guards. UI tests cover CRUD, filters, errors, and
permissions. Run backend `python -m unittest discover -s tests`, frontend `npm test`,
`npm run lint`, `npm run build`, and optionally
`PGLITE_MODULE=<isolated-package>/dist/index.js node --test tests/test_trainer_plan_schema.mjs`.
The repository's existing `.gitignore` ignores `tests` directories; that policy
has not been changed by this feature.

The existing OpenDesign-derived styles and membership alignment fixes are reused.
The OpenDesign daemon was unreachable; responsive checks use rendered fixtures
from the actual React components, not a live authenticated Supabase session.

Verified locally: 60 backend tests, 51 frontend tests and 49 SQL checks passed,
along with frontend lint, strict TypeScript/production build and OpenAPI route
registration. Card/form fixtures were inspected at 1440, 1024, 768 and 390px.
